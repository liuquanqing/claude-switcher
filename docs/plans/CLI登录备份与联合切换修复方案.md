# CLI 登录备份与联合切换修复方案

核验日期：2026-10-31，Asia/Singapore。用户最新要求为先完成规划；本轮未实现或启用下述续期流程。

## 当前判断

**保留现有桌面档案与 CLI 联合切换，先修旧备份接入和续期回写。正常使用仍是点一次“切换”，成功后桌面与默认 CLI 属于同一账号、同一组织。无需用户填写 token。**

参考重点：CCSwitcher 的凭据归属、备份可靠性和错误分类；CC Switch 的官方 CLI 执行及配置目录隔离。暂不迁移成完整的多终端、多目录账号管理器，也不把“仅切桌面”当成一致性目标的完成。

### 已确认的故障

经用户授权，只读检查了出错目标的一条备份，仅输出结构布尔值，未保存或输出凭据：

| 项目 | 结果 |
| --- | --- |
| 访问令牌存在 | 是 |
| 访问令牌已过期 | 是 |
| 刷新凭据存在 | 是 |
| 账号与组织元数据完整 | 是 |
| 新版 `_claudeSwitcherVerification` 存在 | 否 |

安装版本为 1.3.1 / build 20261030.14.0；核查的发布基线为 `e995bb90e8c41b5e22b9ac0db306ab1f572911f1`。该基线与本地候选的拒绝分支相同：旧访问令牌不可用，且缺少新版核验记录，因此在 `CLITransaction.verify` 拒绝恢复。目标还没有进入 CLI 写入、桌面目录移动或重启阶段。

这不是备份丢失或写入失败。刷新凭据“存在”不证明服务端仍接受它；是否可续期仍未知。本轮只读诊断没有尝试真实续期。

原版只保存 OAuth 与账号元数据，不含新版核验记录。原版先退出桌面、移动档案，再尝试 CLI 切换，CLI 失败也继续打开桌面。新版增加了前置验证和还原，却缺少让过期旧备份获得有效核验记录的接入流程。

### 之前测试的准确含义

假数据已验证备份/恢复往返、文件凭据、失败还原；同时明确验证过：过期旧备份被拒绝且目录不动，带核验记录和刷新凭据的过期备份可恢复为待刷新。2026-10-31 针对这两个分支再次执行，2/2 通过。

因此既有测试证明了安全停止，未证明旧备份能自动续期，更未证明真实刷新凭据仍有效。新增验收必须覆盖这条目前缺失的成功路径。

## 价值

让已有原版账号继续可用，让用户不必为短期访问令牌过期反复登录。将“备份已保存”“默认登录已恢复”“在线身份已确认”区分开，只有条件满足才显示联合切换成功。减少因错误提示笼统而反复授权、反复点击切换的情况。

## 目标

1. 兼容旧格式备份；先确认身份，成功后升级保存格式，不凭旧元数据直接补一个可信标记。
2. 需要续期时运行本机未经修改的官方 CLI。程序不自行实现刷新接口，不要求用户复制令牌。
3. 续期产生的新凭据必须持久保存并回读；不能只留内存，不能在恢复失败后删除唯一的新凭据。
4. 联合切换完成后，目标桌面档案与默认 CLI 的账号 UUID、组织 UUID 匹配。账号名和邮箱只供显示。
5. 保留现有读写验证、目录还原、网络门禁与运行中任务边界。

### 拟议用户流程

- **普通切换：** 点“切换”后准备 CLI；有效登录直接复用；旧备份需要续期时自动尝试一次。成功后继续备份、退出桌面、切目录、恢复默认 CLI、核对、启动桌面。
- **系统授权：** macOS 钥匙串可能要求授权，和 Anthropic 登录续期是两回事。不能承诺 ad-hoc 更新后授权永远继承，也不通过扩大钥匙串 ACL 来消除提示。
- **需要重新登录：** 仅当官方 CLI 明确确认登录无法恢复时，提供官方浏览器登录流程；用户不粘贴 access/refresh token。必须确认实际登录的是所选目标账号。
- **临时失败：** 网络、429、超时或存储不可读显示重试原因；保留原登录，不把所有错误都说成“重新登录”。不自动循环请求。
- **当前桌面与 CLI 不一致：** 提供一次明确的“同步 CLI”操作，复用同一个准备和恢复流程。
- **仅切桌面：** 保留现有显式例外；成功后清楚显示 CLI 未同步，不能计作联合成功。不默默降级。

上述是交互语义，不锁定视觉样式和最终文案。前端仍交用户指定的 Kimi；如需替代模型，沿用用户后续明确选择，Codex 仅负责接口、后端及审核。

### 后端流程与凭据边界

```text
检查网络 / 模式 / 当前档案
  → 识别当前默认 CLI 及目标档案的真实身份
  → 目标若已是默认 CLI：优先核验当前新登录，不用旧备份覆盖
  → 其余目标：读取保存备份
      ├─ 可核验有效登录：进入现有准备事务
      ├─ 过期且有刷新凭据：隔离官方 CLI 续期 → 验证 → 保存并回读
      └─ 无备份 / 明确失效：提示官方登录，不清空当前 CLI
  → 保存并回读离开账号的最新 CLI 登录
  → 正常退出 Desktop，等待退出完成
  → 切换桌面目录与默认 CLI，核对身份，失败按阶段还原
  → 再检查门禁，启动 Desktop
  → 展示准确结果
```

采用范围是默认配置的订阅 CLI。显式 `CLAUDE_CONFIG_DIR`、API 环境变量、apiKeyHelper、企业或第三方认证不能被静默覆盖。也不能把 Desktop 的 OAuth 直接当成 CLI 的 OAuth。

**隔离续期工作区是待验证实现，不是已完成能力：** 只用于准备所选目标，不临时替换用户默认 CLI，不复制真实项目、会话或完整设置。需明确官方 CLI 的配置目录、钥匙串 service 派生、文件凭据优先级，以及更新后的实际存储位置；通过适配器契约测试后才接入。

仅传 `CLAUDE_CONFIG_DIR` 不足以证明所有认证来源已隔离。需处理子进程继承的 API 环境变量、设置来源、MCP、hooks 与 cwd；不能修改用户全局设置。保持用户网络配置和门禁，失败或未知不执行续期。

运行官方 `auth status` 可能只返回本地报告，不能当作续期成功证明。`/usage` 退出码为 0、缓存存在或缓存时间变新，也不能单独证明目标完整身份。必须回读实际新凭据，并取得与目标账号/组织对应的有效证据；现有在线 profile 核验如仍有必要，应明确保留，不能宣称全应用已不接触 OAuth。

**续期后保留：** 官方 CLI 可能轮换刷新凭据。先确认工作区和备份存储可写；续期结果应保留在私有原生存储中，核验并回写目标备份、回读成功后才清理本次工作区。若写入失败或身份不符，保留恢复材料，停止联合切换。旧刷新凭据可能已失效，不能以“还原旧文件”声称完整恢复服务端登录。

若失败遗留了本次新的原生凭据，下一次重试先检查它，不再次用旧备份覆盖。工作区需要小型操作收据（目标身份、原备份摘要、阶段、目录引用，不含令牌）以支持此真实失败时序，不引入全局后台任务系统。

**保存当前账号：** 切离前读取当前最新凭据，确认实际归属后回写到对应档案。官方 CLI 续期或其他切换器写入会改变凭据；准备后、提交前按现有事务回读，变化则停止而非覆盖。发现元数据与凭据不一致时不能猜邮箱、不能用新账号覆写旧账号备份。

**成功定义：** 只在默认 CLI 与目标 Desktop 保存身份匹配、必要写入回读通过且 Desktop 启动成功后，报告联合成功。网络门禁拒绝启动、进程未出现、或 CLI 仅恢复为待核验时，应保留对应阶段状态，不统一报“切换完成”。

## 非目标

- 不按额度自动轮换账号，不扩大到全账号后台续期或直接 OAuth 配额轮询。
- 不迁移所有 CLI 会话、项目、MCP 和设置到新目录；不让普通 `claude` 命令改变使用习惯。
- 不终止用户运行中的 CLI 任务，不宣称默认登录等于每个 shell/项目的有效认证。
- 不修改代理、守卫、API 管理器或真实 Desktop 档案；本次规划不安装、发版或推送。
- 不复制上游完整账号中心、复杂切换日志与锁体系；具体新增同步只针对已确认的刷新与写入冲突。

## 风险与冲突

1. **备份刷新后服务端旧令牌失效，而落盘失败。** 上游已有相同失败处理；因此保留原生恢复材料是必要措施。不能只依赖“写入前刚检查可写”。
2. **运行中 CLI 回写元数据或凭据。** 是上游实际遇到的问题。默认登录一致与所有运行任务一致必须分开；本轮不自动结束任务。
3. **另一个工具持有同账号刷新凭据。** 不接受“非活动账号一定只有本程序使用”的假设；不能保证并行工具绝无影响。只按用户操作处理一个目标，发现本地状态变化即停止。
4. **原生 CLI 接口会变化。** `auth status`、`/usage` 与凭据读写路径是兼容契约，不能凭 README 承诺自动续期必定可用。需限定验证版本及失败回退。
5. **钥匙串授权和认证续期不同。** 现有 ad-hoc 签名仍可能在升级后触发授权；本修复不能宣称解决所有密码弹窗，不增加“所有应用可访问”权限。
6. **上游文档与代码不一致。** CCSwitcher 非活动备份直接刷新的事实已由调用点核对；本方案按源码取舍，不采用旧 README 的全部表述。
7. **完整多目录方案超出当前需求。** 会影响会话历史、共享设置和已有默认 CLI 使用习惯，本轮只评估续期准备工作区。

新增日志/收据仅服务已知的凭据轮换与落盘失败；若实现中还要增加未在这里说明的全局锁、自动重试或更多状态，先说明具体触发场景与成本。

## 待决
