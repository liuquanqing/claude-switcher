# 首次安装后桌面账号与用量空白

2026-11-01。发行目标：1.3.4。设备端更新与发行分开验收，未将构建通过当作已安装。诊断与后端修复由 Codex 完成；Kimi 仅在隔离源码副本补了一行无额度窗口时的显示条件，未调用 Claude。

## 已确认的现场证据

经用户授权，通过 SSH 只读核对 MBP16。先从当前 Tailscale 状态确定设备，再将 SSH 公钥与既有可信记录匹配，保持严格主机校验；使用原有专用密钥认证，未新增远端密钥、改 SSH 服务或关闭主机校验。

- 实际运行切换器为 1.3.3 / 20261031.16.0，Claude 桌面为 4.4212.0；桌面主进程确实运行。截图“桌面运行中”已正确表示进程识别成功。
- 桌面有本地账号标识与加密登录缓存，默认 CLI 有完整账号/组织元数据及本机用量缓存；桌面本地账号 UUID 与默认 CLI 相同。
- 切换器当前档案未读到有效快照，因此没有可供卡片匹配的桌面身份。最后一次区分文件不存在/不可读的独立元数据复核因自动审批服务参数错误未执行，不能将这两种情况彻底排除。
- Personal、Business 为初始化档案名，Business 空目录不代表发现了另一个已登录账号。

这些证据不等于远端订阅在线有效性已验证，也没有证明桌面/CLI 的组织已在线核验一致；没有读取或解密钥匙串、运行远端 `/usage`、切换账号、续期登录或读取会话内容。报告不包含邮箱、真实 UUID、令牌、节点和订阅。原始诊断仅留本地 Git 忽略目录。

## 根因

1.3.3 的刷新先读官方 CLI 用量，然后只匹配已有 `snapshot.identity` 的档案。缺少首次建立当前桌面身份的步骤，因此没有旧快照的新机器陷入“无桌面身份 → 用量无法归属 → 一直空白”。这与桌面进程是否运行是不同问题，不应让用户重新登录来掩盖。

## 补丁行为

- 订阅模式刷新先从桌面自己的登录材料确认当前账号，再读取/匹配官方 CLI 用量。不会用 CLI 邮箱或账号 UUID 猜桌面身份，不查询或初始化其他未登录档案。
- 首次通过切换器成功打开桌面时补做初始化；信息已经完整时，普通“显示”不重复触发该初始化。启动被拦截/失败不会继续索取授权。
- 自动刷新仍禁止授权 UI；用户明确刷新或首次明确打开才允许系统授权。首次读取保存登录可能需要系统许可，这不等于重新登录；补丁没有改变钥匙串 ACL 或解决 ad-hoc 跨版本授权问题。
- 身份读取失败、账号/组织不完整、期间档案改变时不猜测；同一身份保留真实用量采样时间，更换身份清除原身份的缓存用量，避免错贴到另一个账号。
- 账号资料与 CLI 报告新关联时保留已有“CLI 报告已登录”结果和核验时间；发现两端不同时显示不一致，不用先前的报告盖住新事实。
- 空白初始化目录不显示为已发现的账号；只有身份、还没有额度窗口时复用原有无用量占位，不显示古老的伪采样时间。Kimi 的修改仅这一条显示条件，周额度单独存在或使用量为 0 仍按真实窗口显示。

只写切换器自身身份/额度快照，未增加直接 OAuth 用量轮询；CLI `/usage` 仍走原来的主动查询与网络门禁。未修改真实登录、账号目录、会话或网络保护规则。

## 守卫提示是另一条边界

现场保存的 managed PID 与当前桌面 PID 相同，但模式配置指纹已不匹配；当前两份模式文件都显示 1p。该条件足以使现有守卫撤销旧登记，不能凭 PID 相同直接接管。

没有据此认定是 Claude、Magpie 或其他程序重写文件，也没有自动改指纹、重新纳入或停守卫。当前规则绑定整个文件代次，普通同模式重写也可能导致重新确认；是否缩小该绑定范围需单独评估，不与本次初始化补丁混合。
