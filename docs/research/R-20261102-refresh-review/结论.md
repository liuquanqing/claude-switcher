# 登录、授权、续期与额度刷新审查

核验日期：2026-11-02（Asia/Singapore）。R-ID：R-20261102-refresh-review。状态：审查完成，修复未实施。范围是默认订阅登录与当前账号，不把默认 CLI 登录等同于所有运行中任务的身份。

## 结论

当前代码的网络门禁、身份归属核验和凭据保留原则应继续保留，但“检测登录 → 必要时恢复 → 核验与备份 → 更新额度”的衔接尚不完整。不建议把当前 RC1 仅因恢复模块测试通过就转成正式版。

使用本仓库真实控制器、假 CLI 和临时 HOME 复现了四个现象：健康的保存身份仍显示未核验；同账号凭据轮换不改变当前身份观察指纹；身份变化仍会被之前的普通失败退避挡住；官方恢复与身份核验成功后，额度读取仍可能是 20 分钟前的缓存。这些是组件复现加源码路径审查，不是使用真实登录完成的端到端验收。

重复密码提示有多种实际来源，不能用上述假数据断言本机所有弹窗都由同一问题造成。当前候选首次从 ad-hoc 换成 Developer ID；不同钥匙串项目与官方 CLI 子进程也具有各自的授权关系。正式签名有助于后续版本身份稳定，但不能承诺所有系统授权从此消失。

## 已确认的问题

### P1：CLI 恢复后额度没有完成刷新

`App/main.swift:435` 的 `refreshAllStatuses()` 在本轮运行过恢复 CLI 后，进入 `refresh(allowInteraction:false)`。`App/CurrentCLIRecoveryController.swift:160` 的切换后补查也有同类路径。该分支只由 `OfficialCLIUsageReader` 读取 `.claude.json` 的缓存，不保证刚才的 `/usage` 已写出新采样；若桌面身份初始化读取还受阻，甚至可能在读 CLI 缓存前返回错误。

`CLICurrentRecovery` 核验的是登录与备份，不负责承诺新额度。不能把 `.renewed`、子进程退出码 0 或“CLI 已与桌面一致”当成额度成功。原 `OfficialCLIUsageReader` 手动命令完成后也未要求缓存采样时间推进；旧缓存虽没有被伪造新时间，用户仍会感到刷新无效。

复现：假 CLI 成功保存新登录，Store 返回 `.renewed`、显示 `.matched`，后续缓存读取却仍得到 1200 秒前的额度。需要将一次官方命令的凭据与额度结果都读回；没有新采样时，网络与身份允许后补一次静默只读额度请求，或明确“登录已恢复，额度未更新”。不为了额度再消耗一次刷新凭据。

### P1：外部登录识别与在线核验混在同一展示状态

每 15 秒的 `observeAccountMetadata()` 调用 `refreshCLI(verify:false)`，只读取保存的身份。冷启动健康登录不需要恢复时，`recoverCurrentCLI()` 返回 `.notNeeded`，不会将这个状态提升为官方报告或在线核验完成。因此“CLI 已经登录，切换器还要我手动刷新”有代码层面的解释，但这不代表系统真的退出登录。

应区分已识别保存身份、官方本地报告已登录、在线核验通过、需要授权及明确失效。后台静默识别无需拿官方子进程反复确认；需要证明在线身份时，再经网络门禁完成一次核验。不能为消除提示把元数据伪装成远端验证。

### P1：同账号重登／凭据轮换的后续动作不及时

`LocalAccountObservation` 包含桌面账号、桌面 token 摘要、CLI `oauthAccount`；不包含 CLI 凭据代次。同账号重新登录且 `oauthAccount` 不变时，当前 15 秒观察信号不变。本轮假文件修改已复现这一点。

独立恢复观察最多每分钟一次，确实还会发现已观察过的凭据版本变化；因此不能说“永远检测不到”。但这次恢复结果没有明确驱动额度立即补查，且冷启动没有旧版本可比较。

`UsageRefreshPolicy` 在处理 `.identityChanged` 前先检查旧 `retryAfter`，当前退避按档案名存储。某次授权／登录不可用造成的普通失败，会让登录已经修好后的请求再等最多约五分钟。修复方向是按账号与凭据代次处理普通失败恢复；服务端 429 的 Retry-After 必须保留，不能因重新登录或手动点击绕过限流。

### P1：手动“刷新”承担过多授权动作

底部入口无条件传 `requestNativeCheck:true`，可能先交互读取原生登录，再启动官方 CLI，读回后核验／写备份，随后还可能读取桌面 Safe Storage 或启动 `auth status`。这不是一个统一的系统授权，涉及至少三类对象：Claude 原生凭据、桌面 Safe Storage、切换器自有备份。`DesktopTokenReader` 已缓存派生密钥，不能把每次桌面 token 读取都说成一次系统弹窗。

`KeychainReadAccess` 和恢复备份写入已禁止后台授权 UI；官方子进程的 macOS 授权则不能由 `--permission-prompts none` 禁止。当前代码如实设置 `guaranteesNoSystemPrompt=false`，因此后台不主动启动官方原生恢复。它能采纳现有 CLI 自行续期的新登录，但不是“后台保证主动续期成功”。

改进应从复用本轮已验证结果、减少重复的交互读取、取消后结束本轮、将恢复动作只留给需要恢复的登录入手。保留稳定 Developer ID 和 Bundle ID；不删除重建真实凭据、不放宽为“任何应用可读”、不改用户钥匙串 ACL 来换取少弹窗。真实系统弹窗次数和具体对象尚未测量，需要今后的无密钥诊断计数与用户反馈补足，不能宣称已经根治。

## 还需补齐的兼容与失败路径

- **环境变量**：当前两个 `/usage` 适配器会保留或继承 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`。CC Switch 的固定实现明确为实际额度请求移除它，因为其目标 CLI 下会使 `/usage` 只读旧缓存。我们的继承行为已由源码确认；本机官方 CLI 在该开关下的具体表现本轮未用真实登录验证。后续仅对本次额度子进程调整，继续分别关闭遥测、错误上报和自动升级，不改用户 shell。
- **超时**：新续期适配器有有界输出与超时后的强制终止；旧 `CLIStatusReader` 和 `OfficialCLIUsageReader` 仅软终止后继续等待。忽略 SIGTERM 的假子进程或长期等待授权时，不能证明它们会在标称 8／45 秒退出。需要统一子进程退出边界，只处理本次新建的辅助进程，不杀已有 CLI。
- **API／第三方模式**：默认 CLI、桌面当前档案、额度所属卡片未必相同。只更新 UUID＋组织唯一匹配的订阅卡；不把 API 余额当订阅额度，不因其配置来源未知而覆盖登录。
- **不活跃账号**：当前默认保留历史额度，不自动轮换所有账号或替它们续期。这是既定范围，应明确显示缓存时间，不向用户暗示全账号实时查询。
- **无五小时窗口**：额度窗口允许缺失；保持已有 weekly-only 行为，不补造 100%、到期时间或五小时倒计时。服务器重置时间经过只触发补查，不能本地猜测额度归零。

## 当前频率与建议

| 动作 | 当前实现 | 建议保持或修正 |
| --- | --- | --- |
| 保存身份观察 | 15 秒，读取本地 JSON；不等于在线登录检查 | 保留，补充同账号凭据代次变化的非交互观察；锁屏／不可读保持 unknown |
| 当前 CLI 恢复观察 | 最多每 60 秒；临期阈值 5 分钟；不能保证无弹窗时不后台启动原生程序 | 保留官方 CLI 作为续期写入者；自然续期／新登录触发后续核验和额度链 |
| 当前额度自动请求 | 活跃 5 分钟、闲置 15 分钟；打开面板、唤醒按数据年龄补查 | 保留；授权完成、身份变化、切换／同步完成时优先收尾，不等下个周期 |
| 普通请求失败 | 五分钟退避；请求间最少 60 秒 | 同一失败版本退避；新的有效登录可解除旧认证失败的退避，429 不解除 |
| 429 | 尊重 Retry-After；缺省再等 15 分钟 | 所有入口共享，包括手动／恢复后补查 |
| 重置倒计时与缓存年龄显示 | 每分钟本地刷新 | 保留，不产生网络流量 |
| 手动刷新 | 可请求授权、恢复、报告核验、额度读取 | 一次动作串联完成，复用结果；不给同一目的重复启动多个官方 CLI |
| 守卫回执读取／服务运行 | GUI 5 秒读状态；服务约 10 秒执行 | 本轮不改变，也不把它当成 CLI 的网络层即时断流 |
| 应用检查更新 | 尚未实现 | 下一版独立加入：每天一次轻量检查，手动检查可即时执行；不与额度刷新绑定 |

以上为调度间隔，不是网络请求完成 SLA。旧超时适配器补齐前不能承诺“点一次固定秒数全部完成”。

## 拟定最小修复顺序

1. 先补底部刷新／切换后收尾的同一轮结果：登录、备份、额度分别记成功或失败，已有官方结果直接复用；无新额度时有明确结果，必要时补一次受门禁的静默查询。
2. 处理外部登录与同账号新凭据的观察信号，解除旧普通认证失败的等待；已有明确失败不得被元数据“洗绿”，服务端限流仍有效。
3. 整理交互凭据读取和官方 CLI 辅助进程，取消即结束本轮，补齐硬截止时间及环境兼容；记录对象类别、次数、结果码，不记录令牌、原始 CLI 输出或真实邮箱。
4. 接入应用检查更新和应用内下载；自动安装再单独验证守卫与回退。前端仍由用户指定的前端作者实施，Codex 仅分析、后端和审查。

本轮只完成审查、复现和规划，未修改生产代码、界面、钥匙串 ACL、已安装应用或守卫。
