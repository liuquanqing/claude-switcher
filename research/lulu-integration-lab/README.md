# LuLu 官方版联动与旧连接阻断验证

2026-11-01（Asia/Singapore）。本轮由 Codex 自行审查，不调用 Claude、Kimi 或其他审查模型。用户边界：隔离验证、不改个人网络和守卫、不读真实账号/会话，优先只断 Claude/Claude Code 的网。

## 源码复核结果

| 需求 | v4.5.5 源码看到的事实 | 当前判定 |
|---|---|---|
| 切换器自动控制阻断 | `App/main.m` 命令行分支为安装/升级/卸载/退出；控制规则和 profiles 的 XPC 要求 LuLu 官方 app 标识、官方签名及 hardened runtime | 未找到可供切换器正常使用的官方控制入口；必须验证签名要求，不绕过校验 |
| 动态切断已放行长连接 | 规则/profile 改动更新内存及磁盘，provider 主要在 `handleNewFlow` 返回 allow/drop；扩展源码未找到显式 `updateFlow` 或入/出站数据回调 | 现有流量撤销机制未得到证明；不能把新连接被拒绝写成旧连接已断 |
| 不影响其他软件 | 有按程序规则与“process + kids”规则；tree 匹配源注释明确祖先按路径匹配、祖先签名未验证，中间父进程退出会断开可追溯关系 | 存在选择性功能，但真实 Claude/CLI/helpers 与无关应用的并行网络覆盖仍 NOT_RUN |
| 控制失联仍阻断 | 告警客户端断开/回复失败时会释放部分等待流并允许；明确已匹配的 block 规则是不同分支 | 原版默认交互策略不等于本项目要求的严格失效关闭；不能笼统说 LuLu 所有规则都会失效 |

“源码未找到”是人工复核加可复现搜索的证据，不是对系统内部行为的完整证明。`signature_gate.swift` 只测必要的静态签名条件；即使官方 app 满足它，也不代表实际 XPC 握手已测通。

## 本轮可实际验证的第一门

在一次性 Mac 取得官方只读包后：

1. SHA-256 与官方发行资产一致，`codesign --verify --deep --strict` 成功，版本确认为 4.5.5。
2. 从精确源码的 `APP_ID`、`SIGNING_AUTH` 生成原版 listener 使用的代码要求。
3. 用系统 Security API 验证：官方 LuLu app 应满足该要求；临时编译的普通切换器身份不满足；即使临时程序使用相同 bundle/signing identifier，换成 ad-hoc 签名仍不满足。临时程序不执行，也不操作任何真实 app。
4. 卸载只读 DMG，保存完成/清理结果与源码摘要。这里的“卸载”仅指 detach 临时磁盘映像，没有安装过系统软件。

这道门失败意味着不能选择“原封不动安装官方 LuLu，然后直接调用内部 XPC”的集成方式。不会用关掉签名校验、改私有 plist、重启过滤器或 GUI 自动点击来包装可靠联动。

## 尚未执行的网络验收

实际过滤器需要系统批准和可控的隔离 Mac 环境。本轮没有这类已激活的 LuLu 测试环境；当前先验证合法控制入口是否存在，**不在个人电脑安装后再试**。

只有控制入口与旧流撤销机制成立后，才有理由进入下一门：

- 同时建立虚构目标客户端、普通终端启动的空白 CLI、无关程序的 IPv4/IPv6、TCP/UDP 新流与持续流。
- 指定规则阻断后，目标双向数据和新流应停止；无关程序持续成功，目标进程仍存活。
- 桌面/CLI/helpers、代发 DNS、代理外层连接分别确认归属；不以整个 Terminal/Node/Python 被封锁充数。
- 注入代理断开、假 JP/未知/过期证据、控制器退出、过滤器暂停/崩溃与恢复，按服务端唯一标记和抓包判断，不只看 UI。
- 保留正确路径恢复正向对照；关闭提示、取消桌面退出不恢复网络。

本轮不会伪造一个“模拟 LuLu”的转发器，然后用它证明官方 LuLu 已能切断长连接。若第一门不成立，后续包级测试明确记 NOT_RUN，而不是继续安装不具备可用控制方案的执行器。

## Codex 审查边界

官方签名发行版可以直接由用户按系统流程批准；自建修改版不能沿用作者签名。若必须改 LuLu 的授权接口或旧流处理，它将成为需要重新签名、部署和验收的二次开发，不再是原版即插即用。GPL-3.0 许可与分发方式也应按实际复用核对，本轮没有打包第三方二进制。

当前产品接入 **HOLD**。未修改产品 App/Sources/build、main、发行标签、应用安装、个人代理/防火墙/守卫、钥匙串或真实会话。

## 本轮实测回执与结论

精确测试提交 `188d9030d5c9a93d5c90541c421e96c32af8cb94` 的[一次性 Mac 实验 41222533548](https://github.com/liuquanqing/claude-switcher/actions/runs/41222533548)完整成功，macOS 15.7.9、x86_64。官方 DMG 摘要、包签名、版本与源码标签已一致核对；只读卷正常 detach。

系统 Security API 的三个静态代码要求结果为：

| 测试对象 | 是否满足原版 XPC listener 的必要签名要求 |
|---|---|
| 官方 LuLu app | 是，状态 0 |
| 临时普通切换器身份 | 否，状态 -67050 |
| 相同 LuLu 标识但不同签名的临时程序 | 否，状态 -67050 |

这是实际系统签名条件验证，**不是已经连接并调用 XPC**。必要条件不满足已经足以排除“让目前切换器直接调用原版内部控制接口”的路线；不会尝试绕过它。

Codex 进一步复核了 app 入口、Info.plist、规则导入及 profile 切换：没有找到用于自动改规则的命令行参数或 URL/scripting 入口；规则导入是 GUI 流程。profile 切换重载规则/偏好；已保存的 block rule 可作用于后续判定，但不能据此推出之前 allow 的长连接被追踪并撤销。源码的等待队列是 paused flows，不等于全部已放行的持续连接。

因此，**LuLu v4.5.5 官方版目前不作为可直接接入的自动断流后端**。既有连接、实际 Claude/CLI 选择性、过滤器故障时行为均仍为 NOT_RUN；不能因为本轮 job 成功就改成 PASS。在合法控制入口与旧流撤销机制尚未成立时，没有启用过滤器做故障注入，不在当前工作电脑补测。

失败准备记录：[首轮 41222260588](https://github.com/liuquanqing/claude-switcher/actions/runs/41222260588)已完成包校验及清理，但单文件 Swift `@main` 编译缺少 `-parse-as-library`，没运行到签名条件测试。探针已修正并保留编译错误输出；首轮 `experimentCompleted=false`，其旧状态字段不能用作签名条件已测的证据。

完整结果位于 `evidence/41222533548/`，摘要为 `validation-receipt.json`。第三方完整源码和二进制没有提交进仓库。

## 后续可选路线（未开始开发）

- 上游提供受支持的外部控制接口及已放行旧流撤销能力，再重新做网络级验收。
- 修改 LuLu 需要新的接口权限设计、签名、部署与完整验收；开源不意味着修改版还能沿用原作者签名。
- 另一种架构是 LuLu 长期禁止目标直连，只让目标经过专用本地代理，由代理控制数据通道。它需要新增并维护代理组件、让桌面及各种 CLI 真正使用该路径，还涉及原有已建立直连的处置，不能当成现有 TUN 方案的无成本替换。本轮没有实现、测试或接入此替代架构。

不选择原版不具备的动态接口，并不等于 LuLu 作为通用出站防火墙没有价值；只是它目前没有满足本项目这组更严格的自动化与存量连接要求。
